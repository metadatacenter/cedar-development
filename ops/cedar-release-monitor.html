Execution map · phase vs. time

The full sequence — run top to bottom

Everything to cut a release: connect, verify auth, build a train, rehearse the preflight, run it, watch it, and recover if a phase fails. Commands use the versions from CONFIG (change those for your release). cedarcli is a shell alias — run it in an interactive cedar shell, not a plain script.

AConnect

Log in, become the build user, start a tmux so the ~1h50m run survives a disconnect.

ssh youruser@your-build-server
sudo su - cedar
tmux
gocedar

0Auth probe

Confirm the GitHub token is valid before a long run, and make every git op fail fast instead of hang.

export GIT_TERMINAL_PROMPT=0
git ls-remote https://github.com/<org>/<a-private-repo>.git HEAD \
  >/dev/null 2>&1 && echo AUTH_OK || echo AUTH_FAIL
Why: an expired PAT makes a private-repo git pull hang forever at a silent Username: prompt. GIT_TERMINAL_PROMPT=0 turns that hang into an instant error. On AUTH_FAIL: refresh the PAT (SSO-authorize if the org needs it), then cd $CEDAR_HOME/<a-private-repo> && git pull once to re-cache it. Keep the export set for the whole run.

1Build a train

A release consumes a train rather than building one. The train builds and verifies the coordinated source state first.

cedarcli publish train           # note the TRAIN_ID it prints
Why a train: the release takes the train's exact source commits, so it never compiles from a moving target.

2Export the Nexus credentials

Nexus reads fall back to anonymous and succeed either way, so an unset credential is invisible until the first upload. Preflight authenticates them for you, but they have to be in the environment first.

export BMIR_NEXUS_USERNAME=...   # from the bmir-nexus-releases server
export BMIR_NEXUS_PASSWORD=...   # entry in ~/.m2/settings.xml
export GIT_TERMINAL_PROMPT=0

3Rehearse — the preflight

Settles every precondition a release can check before it changes anything, in about a minute.

cedarcli release plan \
  --version {{VER}} \
  --next-version {{NEXT}} \
  --from-train <TRAIN_ID> \
  --cee-version <PUBLIC_CEE_VERSION>
Expect: the CEE byte-equivalence proof, Preflight: every precondition settled, and No changes made. A blocking finding names the exact command that clears it. Nothing irreversible has happened yet.

4Run the release

The same preflight runs again, so the release cannot begin from a state the rehearsal would have refused.

{ cedarcli release start \
    --version {{VER}} \
    --next-version {{NEXT}} \
    --from-train <TRAIN_ID> \
    --cee-version <PUBLIC_CEE_VERSION>; echo "CEDARCLI_EXIT=$?"; } 2>&1 | tee /tmp/cedar-release.log
~1h50m. Leave it in tmux; detach with Ctrl-b d and it keeps running. Transient connection failures are retried with backoff; a changed tree or a failed verification still stops it at once.

5Watch it

The ledger, rather than the log, is the source of truth.

cedarcli release status
tail -f /tmp/cedar-release.log

6Finish

Acceptance is the last phase, and it proves the release from outside the ledger that recorded it.

cedarcli release status | grep Phase        # expect: accepted
Only accepted means done. Acceptance re-asks whether every repository carries {{TAG}}, every remote ref stands where the ledger says, every published artifact still matches its recorded bytes, and the frontends pin the proven CEE. Treat any other final phase as an incomplete release.

RIf a phase fails — resume, don't restart

The failure is recorded and the failed attempt is retained as evidence under ~/.cedar/train-releases/attempts/{{VER}}/. Nothing is rolled back and nothing is deleted.

cedarcli release status         # the recorded phase and failure
cedarcli release resume         # continue from it
Resume re-verifies every completed ref, build log, generated-output hash, Maven byte, npm tarball, and registry inventory before continuing. Drift in any of them is a hard stop. Never edit a ledger or manifest by hand — those files are the release's record of what it verified.

NNotes

Branch layout: the release repos publish from main; the skip_from_release frontends build from develop. The release arranges this itself — do not force a blanket cedarcli git checkout main, which sweeps those onto their stale main.

Red CI after a release now means something. The snapshots are deployed before the remotes are integrated, so the CI each develop push triggers finds the parent and libraries already in Nexus. Releases cut before that change left a tail of red builds that passed unmodified on a re-run.
