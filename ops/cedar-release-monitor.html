Execution map · phase vs. time

Eight sequential phases of release all-in-one. The bar colors, NOW marker, and finish estimate are computed live in the browser off the start time in CONFIG; teal ticks are checkpoints you record as it runs. Phase durations are estimates from prior clean runs (typically ~1h50m–2h30m end to end); open any row for its real sub-steps and exact task counts.

done running pending live NOW ▏ = recorded checkpoint

The full sequence — run top to bottom

Everything to cut a release by hand: connect, verify auth, pre-flight build, dry-run the versions, run it, watch it, and recover if it stalls. Commands use the versions from CONFIG (change those for your release). cedarcli is a shell alias — run it in an interactive cedar shell, not a plain script.

AConnect

Log in, become the build user, start a tmux so the ~2h run survives a disconnect.

ssh youruser@your-build-server
sudo su - cedar
tmux
gocedar

0Auth probe

Confirm the GitHub token is valid before a long run, and make every git op fail fast instead of hang.

export GIT_TERMINAL_PROMPT=0
git ls-remote https://github.com/<org>/<a-private-repo>.git HEAD \
  >/dev/null 2>&1 && echo AUTH_OK || echo AUTH_FAIL
Why: an expired PAT makes a private-repo git pull hang forever at a silent Username: prompt. GIT_TERMINAL_PROMPT=0 turns that hang into an instant error. On AUTH_FAIL: refresh the PAT (SSO-authorize if the org needs it), then cd $CEDAR_HOME/<a-private-repo> && git pull once to re-cache it. Keep the export set for the whole run.

1Refresh + pre-flight build

Pull the merged branches, re-source the shell, then compile everything — so a bad merge surfaces in ~20 min, not 2 hours.

cedarcli git checkout develop && cedarcli git pull && cedarcli clean maven all
exec bash -l                 # re-read the freshly-pulled env / aliases / cedarcli
export GIT_TERMINAL_PROMPT=0
cedarcli build all           # ~20 min; ends with "Execution succeeded"
Why re-source: a pull can update the CEDAR profile, aliases, or cedarcli itself; the current shell holds the pre-pull versions until a fresh login shell.

2Dry run — the version guardrail

Generate the whole plan without executing anything, then verify only the intended versions appear.

export CEDAR_RELEASE_VERSION={{VER}}
export CEDAR_NEXT_DEVELOPMENT_VERSION={{NEXT}}
cedarcli env release                        # confirm the two versions
cedarcli release all-in-one --dump-plan     # builds the plan, runs nothing

# verify the plan (only your two versions should appear):
grep -oE '[0-9]+\.[0-9]+\.[0-9]+(-SNAPSHOT)?' ~/.cedar/last_plan_content.sh | sort | uniq -c
Expect: tag {{TAG}}, branches release/pre-{{VER}}/… + release/post-{{NEXT}}/…, and only {{VER}} / {{NEXT}} — no stray older versions, no {{VER}}-SNAPSHOT. Nothing irreversible has happened yet.

3Run the release

The real thing — merges to main/develop, pushes, tags, then deploys to Nexus + npm. Tee to a log so it's watchable.

{ cedarcli release all-in-one; echo "CEDARCLI_EXIT=$?"; } 2>&1 | tee /tmp/cedar-release.log
~1h50m–2h30m. Leave it in tmux; detach with Ctrl-b d and it keeps running.

4Watch it

From any shell on the box:

tail -f /tmp/cedar-release.log
# landmarks only:
tail -f /tmp/cedar-release.log | grep -E "Updating|Execution|BUILD (SUCCESS|FAILURE)|-> (main|develop)|npm notice"

!The exit code lies

On a mid-run failure cedarcli prints Execution halted but still exits 0. Never trust $? — grep the log.

grep "Execution succeeded" /tmp/cedar-release.log      # the real success signal
grep -E "Execution halted|remote rejected|Return code: [1-9]|BUILD FAILURE|npm ERR!" /tmp/cedar-release.log

5Verify

Confirm the release landed on every repo.

cedarcli check versions
cedarcli git list tag | grep {{TAG}}         # tag pushed everywhere
# each release repo should show main at {{VER}}, develop at {{NEXT}}

RIf it halts mid-commit — resume, don't roll back

A halt in the commit phase leaves some repos pushed and some not. The commit pushes are the historical soft spot (transient GitHub push errors such as fatal error in commit_refs). Finish forward.

cedarcli release commit        # no args → prints the exact resume command; then run it
cedarcli release cleanup       # no args → prints its command too
Why not rollback: release rollback only deletes the branch + tag — it does not un-push merges already landed on main/develop, so rollback + rerun collides. release commit is idempotent: already-done repos no-op ("Everything up-to-date"), the rest complete and retry the failed push. If a transient GitHub push is rejected, re-running the same push usually just works.

NNotes

Branch layout for the deploy: the ~48 release repos deploy from main; the 5 skip_from_release frontends (artifact-viewer, embeddable-editor, model-typescript-library ×3) build from develop. release all-in-one sets this up itself — do not force a blanket cedarcli git checkout main, which sweeps those onto their stale main.
